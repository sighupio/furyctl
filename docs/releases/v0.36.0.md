# furyctl release v0.36.0

Welcome to the latest release of `furyctl` maintained by SIGHUP by ReeVo team.

This release adds support for SIGHUP Distribution v1.36.0 and for the v1.35.2 and v1.34.3 patch releases, including the new Utilities core module. It also brings new commands, like `furyctl create secrets` and `furyctl renew kubeconfigs`, and a series of new features and bug fixes for the Immutable and OnPremises kinds.

## New features 🌟

- [[#741](https://github.com/sighupio/furyctl/pull/741)] Immutable, OnPremises: furyctl now checks the PKI folder from the configuration file before an apply. When the folder or one of its files is absent, the apply stops before it starts the playbooks, and the message names the `furyctl create pki` command to run. Before this release, the apply failed in the middle, inside an Ansible task, with a message that did not say how to correct the fault. `furyctl validate config` does the same check, so a pipeline that validates a configuration now needs the PKI folder on that machine.
- [[#756](https://github.com/sighupio/furyctl/pull/756)] All kinds: the new `furyctl create secrets` command creates the random secrets that a configuration file needs. For example, Pomerium needs four secrets when the authentication provider type is `sso`. It writes one file for each secret and the `--update-config` flag writes the `{file://<path>}` references in `furyctl.yaml` for you. For the components, the flags and the behavior of each one, see `furyctl create secrets --help`.
- [[#756](https://github.com/sighupio/furyctl/pull/756)] OnPremises and Immutable: `furyctl create secrets` asks whether the cluster encrypts the secrets of etcd at rest. With an answer of `yes` it writes an EncryptionConfiguration object with a new secretbox key. The API server gets that configuration with the next kubernetes phase of an `apply`. The secrets that etcd already holds stay in clear text until something writes them again.
- [[#745](https://github.com/sighupio/furyctl/pull/745)] OnPremises and Immutable: the new `furyctl renew kubeconfigs` command renews the kubeconfig file of the admin and the kubeconfig files of the users in `spec.kubernetes.advanced.users.names`. It writes them to the working directory, with the names that `furyctl apply` uses. A list of names renews only some of them, for example `furyctl renew kubeconfigs admin alice`. A user that you add to the configuration file gets a kubeconfig file. It is not necessary to apply the kubernetes phase.
- [[#764](https://github.com/sighupio/furyctl/pull/764)] Immutable: the infrastructure phase now upgrades the load balancers, which covers the operating system, the system extensions and the configuration. Before this release the phase wrote "not implemented yet" and did nothing, so an upgrade left the load balancers as the installation made them. `apply --upgrade-node <host>` now accepts a load balancer as well as a worker node. It stops for a control plane host, an etcd host and a host that the configuration does not hold. Before this release it accepted any name and upgraded nothing. On kind Immutable, `--upgrade-node` now selects its own phase. The role of the host decides it, so `--phase`, `--start-from` and `--post-apply-phases` stop when you give one of them with it. Kind OnPremises keeps its behavior, because its kubernetes phase upgrades every host that `--upgrade-node` names. A distribution released before this feature holds no load balancer playbook, and furyctl then writes a warning and continues with the other phases.
- [[#772](https://github.com/sighupio/furyctl/pull/772)] All kinds: while an Ansible playbook, a script or `helmfile apply` runs, furyctl now shows its last 10 lines of output in a region of the terminal, and removes them when it completes. The scripts include the upgrade scripts and the `kapp deploy` of the distribution phase, which before this release showed only one line for many minutes. The region is off with `--debug`, `--no-tty` and `--log stdout`.
- [[#778](https://github.com/sighupio/furyctl/pull/778)] EKSCluster: while `terraform init`, `plan`, `apply` or `destroy` runs, furyctl now shows the last 10 lines of output in the same region. For `apply`, furyctl shows only the message of each JSON line.
- [[#779](https://github.com/sighupio/furyctl/pull/779)] Immutable: the infrastructure phase no longer waits for the machines to boot when every node answers and no change needs a node provisioned again. Before this release, every apply on a running cluster stopped at the assets server until you pressed ENTER. To provision a node again, erase its disk and power it off before the apply, then boot it from the network while furyctl waits. A distribution released before this feature keeps the wait.
- [[#783](https://github.com/sighupio/furyctl/pull/783)] Immutable, OnPremises and KFDDistribution: one `apply` now installs the full distribution on a new cluster. When the cluster has no default StorageClass, the distribution phase skips the packages that need one (`dr`, `logging`, `tracing` with tempo, `prometheus-operated`, `mimir`). Before this release they stayed skipped until you applied the distribution phase again. Now furyctl checks again after the distribution phase and after the plugins phase. When a default StorageClass is there, furyctl applies the distribution phase again and logs why. For a StorageClass provider in `spec.distribution.customResources`, this happens before the plugins phase. After the plugins phase, furyctl waits up to 2 minutes for the StorageClass, but only when the plugins phase applied plugins. `--phase distribution` checks again one time, after the phase. `--dry-run` does not apply the phase again.
- [[#785](https://github.com/sighupio/furyctl/pull/785)] Immutable: the table of the node bootstrap status now has a SOURCE IP column. The column shows the IP address from which each node sent its last status. Use it to find a node that boots on an unexpected network or NIC.
- [[#786](https://github.com/sighupio/furyctl/pull/786)] OnPremises and Immutable: furyctl now supports the Utilities core module introduced with SIGHUP Distribution v1.36.0. It downloads the module from its canonical `module-utilities` repository while preserving the existing repository-name fallbacks, and `furyctl get cluster-info` shows its version and the selected Headlamp authentication type.
- Immutable, OnPremises and KFDDistribution: `furyctl diff` now shows the Kubernetes resources that an `apply` would create, update or delete, next to the comparison of the configuration. It prints one report on the standard output: the `Configuration` section, then the `Distribution` section and one section for each kustomize plugin and each helm release. Each change is one line, `+` for a create, `~` for an update and `-` for a delete. The report ends with the plan, and it warns about each Namespace or CustomResourceDefinition that the `apply` would delete with everything in it. A line `Not shown:` lists what the report does not cover: the cleanups, migrations and upgrade steps that `apply` runs outside kapp, the resources that kapp may replace, and the plugins that you removed from the configuration. `furyctl diff` writes nothing to the cluster. The distribution phase is compared with the new `scripts/diff.sh` of the distribution, which kapp runs with `--diff-run`; with a distribution that has no `diff.sh`, furyctl writes that the section is not supported by that distribution and still compares the helm releases. The flags `--phase distribution` and `--phase plugins` limit the report to that phase, and `--phase infrastructure` and `--phase kubernetes` have no plan to show.
- Immutable, OnPremises and KFDDistribution: the local side effects of `furyctl diff` are the same as the first steps of `apply`. It runs the preflight, which on Immutable and OnPremises connects to the nodes over SSH and writes `admin.conf` in the run dir. It renders the distribution and the plugins into the same run dir as `apply`, so do not run `diff` and `apply` at the same time. For the helm releases it runs `helmfile init`, which installs the helm plugins and adds the helm repositories on the machine, as `apply` does. It downloads and validates the dependencies as `apply` does; `--airgap-bundle` skips the download.
- All kinds: the new flag `--config-only`, or `configOnly: true` in the `diff` section of `flags`, makes `furyctl diff` do what it did before this release: compare only the configuration with the one stored in the cluster, with the same output and exit code. It downloads no dependency, runs no preflight and renders nothing.

## Bug fixes 🐞

- [[#743](https://github.com/sighupio/furyctl/pull/743)] All kinds: `apply --start-from` now stops when the configuration has changes to a phase before the selected one. Before this fix furyctl skipped those changes and wrote the new configuration to the cluster, so the change was lost and the next `diff` did not show it as pending.
- [[#746](https://github.com/sighupio/furyctl/issues/746)] All kinds: a flag that you give on the command line now has precedence over the same flag in the `flags` section of `furyctl.yaml`. The documented priority is `furyctl.yaml` < environment variable < command line. Before this release the commands `diff`, `create config`, `get cluster-info` and `get upgrade-paths` read the configuration file first, thus the configuration file had the precedence. If you want the value of the configuration file, do not give the flag on the command line.
- [[#746](https://github.com/sighupio/furyctl/issues/746)] All kinds: the `validate`, `download`, `connect`, `renew` and `dump` sections of the `flags` field of `furyctl.yaml` now work. The documentation lists these sections. Before this release furyctl dropped them. The validation of the configuration file also stopped with `unsupported flags command`. furyctl does not accept a `tools` section any more, because it has no `tools` command.
- [[#739](https://github.com/sighupio/furyctl/pull/739)] Makes furyctl distinguish an error "the cluster doesn't exist yet" from any other preflight failure on OnPremises clusters. Supports both the renamed `fetch-admin-conf-playbook.yaml` and the legacy `verify-playbook.yaml` used by older SD versions.
- [[#750](https://github.com/sighupio/furyctl/issues/750)] All kinds: the `flags` section of `furyctl.yaml` now accepts every flag of its commands. `delete` accepts `force`, `skipDepsDownload`, `skipDepsValidation` and `vpnAutoConnect`. `get` accepts `format`, `from` and `kind`. Before this release furyctl stopped with `flag 'X' is not supported`, although the command has the flag. The documentation of the `flags` section now gives the same list of flags as furyctl accepts.
- [[#754](https://github.com/sighupio/furyctl/pull/754)] OnPremises: after `apply --upgrade --skip-nodes-upgrade`, a later `apply --upgrade` now upgrades only the worker nodes that are still pending or failed, one at a time. furyctl saves the result after each worker node, so an interrupted upgrade continues from the remaining nodes. While worker nodes are pending, a plain apply and partial upgrade options stop to prevent an unsafe apply; `--force upgrades` or `--force all` allows partial upgrade options to continue with a warning.
- [[#759](https://github.com/sighupio/furyctl/pull/759)] Immutable: surface butane-to-ignition translation errors to the user.
- [[#762](https://github.com/sighupio/furyctl/pull/762)] furyctl local cache was not being invalidate when commits have landed on the upstream. Now it does.
- [[#764](https://github.com/sighupio/furyctl/pull/764)] Immutable: furyctl no longer stops with a panic when it resumes an upgrade whose stored state does not hold every phase. A state that an older furyctl version wrote has no infrastructure sub-phases, and the load balancer upgrade writes them. furyctl now reads the stored state over a complete one, so every phase exists. It still reads the state as it was stored for the decision of which phase to resume from.
- [[#766](https://github.com/sighupio/furyctl/pull/766)] Immutable: `apply --upgrade --skip-nodes-upgrade` now records the worker nodes that it does not upgrade. Before this release furyctl stored the configuration of the new version as a complete upgrade. The cluster then reported a version that the worker nodes did not run, and the next `apply --upgrade` found no difference between the two versions and upgraded nothing.
- [[#793](https://github.com/sighupio/furyctl/pull/793)] Immutable, OnPremises: if `apply --upgrade` stops before it completes, `apply --upgrade-node <host>` now stops with a message that names `furyctl apply --upgrade --skip-nodes-upgrade` to complete the upgrade. Before this fix, the message was `upgrade flag not set by user`, and it did not tell you that the upgrade was incomplete.
- [[#795](https://github.com/sighupio/furyctl/pull/795)] Immutable, OnPremises: `apply --upgrade-node <host>` now stops when the configuration file has changes, and names the command to run first. Before this fix, the run applied only the playbook of the host, but it stored the changed configuration as applied. A later `apply` or `furyctl diff` then did not see the changes.
- [[#767](https://github.com/sighupio/furyctl/pull/767)] Immutable: `apply` no longer stops with `error during server shutdown: context deadline exceeded` after the machines boot. The assets server waited for a request that a reset machine left open, and the timeout of that wait failed the infrastructure phase although every machine had booted.

- [[#770](https://github.com/sighupio/furyctl/pull/770)] Immutable: `apply --phase distribution` and `apply --phase plugins` now stop when the cluster does not exist. Before this release they continued, and they applied to the cluster of the current kubeconfig context. The preflight check now also says when it cannot reach a control plane host, instead of reporting a cluster that does not exist.
- [[#774](https://github.com/sighupio/furyctl/pull/774)] Immutable: the preflight check now reads every host, and not only the control plane hosts. When other hosts belong to a cluster and no control plane host gives its kubeconfig, the apply now stops. Before this release, furyctl continued as if the cluster did not exist. The check also names each host that does not answer.
- [[#776](https://github.com/sighupio/furyctl/pull/776)] OnPremises and Immutable: the ansible that furyctl installs now works when the `--outdir` path contains a symlink, for example `/tmp` on macOS. Before this fix the link to the ansible venv was broken in that case, and each playbook failed with `no such file or directory`.
- [[#780](https://github.com/sighupio/furyctl/pull/780)] All kinds: furyctl now writes the error that stops a command to the log file, and not only to the terminal. Before this release the log file did not have this error.
- [[#781](https://github.com/sighupio/furyctl/pull/781)] All kinds: the mise that furyctl bundles no longer reads your own mise configuration or your `MISE_*` and `__MISE_*` environment variables. Before this fix it read the settings of `~/.config/mise`, `/etc/mise`, the `mise.toml` files of the current directory and its parents, and the environment.
- [[#782](https://github.com/sighupio/furyctl/pull/782)] All kinds: on SIGINT or SIGTERM, furyctl now stops the tools that it runs, for example ansible, terraform and kapp, and waits for them to exit. Before this fix furyctl exited at once, and the tools stopped abruptly at their next output. terraform could then keep the state lock.
- [[#787](https://github.com/sighupio/furyctl/pull/787)] OnPremises: `furyctl delete cluster` no longer deletes the distribution from the cluster of the current kubeconfig context when the preflight check finds no cluster. It now skips the distribution phase and runs the kubernetes phase only, and `furyctl delete cluster --phase distribution` stops with an error.
- [[#758](https://github.com/sighupio/furyctl/issues/758)] All kinds: furyctl now removes the temporary copy of the distribution when the command ends, also on an error, and on SIGINT or SIGTERM after the download. Before this fix, each command left a `furyctl-*` folder in the temporary directory, up to 100 MB each with a local `--distro-location`.

## Breaking Changes 💔

- [[#764](https://github.com/sighupio/furyctl/pull/764)] Immutable: `apply --upgrade-node <host>` now stops when you give `--phase`, `--start-from` or `--post-apply-phases` with it. Before this release furyctl accepted these together. `--phase kubernetes` did the same work as `--upgrade-node` alone, and the other two did no extra work without a message. Give `--upgrade-node` alone. Kind OnPremises is not affected.
- [[#750](https://github.com/sighupio/furyctl/issues/750)] All kinds: furyctl does not accept five flags in the `flags` section of `furyctl.yaml` any more. These are `create.provider`, `create.name`, `create.version`, `delete.startFrom` and `delete.autoApprove`. No command has them, thus furyctl accepted them and then did nothing. Remove them from your configuration file. Until you remove them, every furyctl command that you run in that directory stops with the message `flag 'X' is not supported`. furyctl validates the complete `flags` section at each start, also for the commands that do not read the section.
- All kinds: **BREAKING for scripts.** `furyctl diff` has a new default output and exit code. It prints the report of the previous items and exits with 1 when a section could not be compared, for example when the cluster is not reachable, when the preflight fails or when a diff command fails. Before this release it printed `Differences found from previous cluster configuration:` and the changed fields, and exited with 0 when it could read the stored configuration. A script that parses the old output or its exit code must give `--config-only`, which keeps the old behavior byte for byte. Sections that are out of scope, like the resources of an EKSCluster, or not supported by an old distribution, do not change the exit code.
- All kinds: `--distro-patches` caveat of `furyctl diff`. The distribution phase is rendered with the `scripts/diff.sh` template, which shares the `define` blocks of `_helpers.tpl` with `apply.sh`. A patch that replaces `_helpers.tpl` must carry the new `define` blocks, or the render of `apply.sh` breaks. A patch that changes `apply.sh.tpl` is not mirrored by `diff.sh`, so the report does not show what that change does.
- EKSCluster: `furyctl diff` does not compare the resources of an EKSCluster yet. Its Distribution and plugins sections say `not compared: EKSCluster is not supported by furyctl diff yet`, only the `Configuration` section is compared, and the exit code is 0 when that section succeeds.
